# Helpdesk

AI-powered support ticket management system. Support emails become tickets; Claude classifies them, writes summaries, and suggests replies for agents.

- `project-scope.md` — features, ticket statuses/categories, user roles
- `tech-stack.md` — chosen technologies
- `implementation-plan.md` — phased task list; tick items off (`- [x]`) as they are completed

## Structure

Bun workspace monorepo with a single root `bun.lock`:

- `client/` — React 19 + TypeScript + Vite 8 + Tailwind CSS v4 (`@tailwindcss/vite`) + shadcn/ui. Dev server on :5173 proxies `/api` to the server.
  - `src/pages/` — route pages; `src/components/` — app components (`NavBar`, `ProtectedLayout`, `AdminRoute`); `src/components/ui/` — shadcn components; `src/lib/` — `auth-client.ts` (Better Auth), `query-client.ts` (TanStack Query client + `errorMessage`), `utils.ts` (`cn`).
  - `components.json` — shadcn config. `src/index.css` holds the shadcn theme (CSS variables for light/dark) and is the only CSS file.
- `core/` — code shared by client and server, published to both as the workspace package `core` (`"core": "workspace:*"`). No build step: `package.json` `exports` points at `src/index.ts`, and Vite and Bun both consume the TypeScript source. Holds zod schemas in `src/schemas/<resource>.ts`, re-exported from `src/index.ts`. Must stay runtime-agnostic (no Node/Bun/DOM APIs, no Prisma, no React); its only dependency is `zod`.
- `server/` — Express 5 + TypeScript, run directly by Bun (no build step). `src/app.ts` defines the app (middleware, auth, `/api/me`, 404/error handlers) and mounts feature routers from `src/routes/` — one `express.Router()` per resource, e.g. `routes/users.ts` mounted at `/api/users`; put new endpoints for a resource in its router, not in `app.ts`. `src/index.ts` starts it on `PORT` (default 3000).

## Commands

Run from the repo root:

- `bun install` — install all workspace dependencies
- `bun run dev` — start client and server together
- `bun run dev:client` / `bun run dev:server` — start one app
- `bun run build` — production build of the client
- `bun run typecheck` — typecheck the e2e files (root `tsconfig.json`), then `core`, then the server, then typecheck + build the client

- `bun run test` — `core` schema tests, then server unit tests, then client component tests, run once (see "Server unit tests" and "Component tests" below)
- `bun run test:e2e` — Playwright end-to-end tests (`test:e2e:ui` for UI mode, `test:e2e:report` for the last HTML report)

Run from `server/`:

- `bun run db:migrate` — apply Prisma migrations (`prisma migrate dev`)
- `bun run db:generate` — regenerate the Prisma client into `src/generated/prisma` (also runs on `bun install`)
- `bun run db:seed` — create the initial admin from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` (idempotent)
- `bun run db:seed:ai-agent` — create the AI Agent user (see "Auto-resolution") and assign it the resolved tickets that already have an AI reply (idempotent)
- `bun run db:studio` — open Prisma Studio
- `bun run jobs:classify-unclassified` — queue AI classification for every ticket with no category, skipping tickets that already have a queued or retrying job (`src/classify-unclassified.ts`; the running server's worker does the work)

Add dependencies from inside the workspace directory (e.g. `cd server && bun add <pkg>`). Keep `zod` on the same version range in `core`, `client` and `server` so there is a single copy.

## Authentication

Better Auth with email + password and database-backed sessions (PostgreSQL via Prisma).

- **Server config** — `server/src/auth.ts`. Uses the Prisma adapter, with no cookie cache, so every session check hits the `session` table and sign-out/revocation takes effect immediately. `trustedOrigins` is `CLIENT_ORIGIN`.
- **Sign-up is disabled** (`disableSignUp: true`). There is no public registration: the first admin comes from `bun run db:seed`, and admins will create agents (Phase 2). To create a user in code, use `auth.$context` → `internalAdapter.createUser` + `linkAccount` with a hashed password, as `src/seed.ts` does. `createUser` silently drops any field not registered in Better Auth's config — a new `User` column must be added to `user.additionalFields` or it falls back to its database default (this is how the first seeded admin ended up as `AGENT`).
- **Routes** — Better Auth handles everything under `/api/auth/*` (`app.all("/api/auth/*splat", toNodeHandler(auth))`). It must stay mounted **before** `express.json()`, because it reads the raw body.
- **Protecting API routes** — add the `requireAuth` middleware (`server/src/middleware/requireAuth.ts`). It returns 401 JSON when there is no session; otherwise it puts `user` and `session` on `res.locals`. Type the handler as `Response<unknown, AuthLocals>` to get them typed. `GET /api/me` is the example.
- **Schema** — `user`, `session`, `account`, `verification` tables in `server/prisma/schema.prisma` follow Better Auth's core schema. Passwords live in `account.password` (`providerId: "credential"`), not on `user`. If you change Better Auth config or plugins, update the Prisma schema to match and migrate.
- **Roles** — `User.role` is a Prisma enum `ADMIN | AGENT` (default `AGENT`). It is registered as a Better Auth `user.additionalFields` entry (`input: false`, so clients can't set it), so `session.user.role` / `res.locals.user.role` are available and typed. The client mirrors the field with `inferAdditionalFields` in `auth-client.ts` — keep the two in sync.
- **Role enum — always use `Role`, never role strings.** The database enum is the Prisma `Role` in `schema.prisma`. `core/src/schemas/users.ts` mirrors it as a zod enum: `roleSchema = z.enum([...])`, plus `Role = roleSchema.enum` (values) and `type Role` (the union). Both have the same shape, `Role.ADMIN` and `Role`. Keep the two lists in step.
  - **Import:** server — `import { Role } from "../generated/prisma/enums.ts"` (relative to the file); client — `import { Role } from 'core'`. Never import the server's generated files from client or `core` code, and never define another copy or a `'ADMIN' | 'AGENT'` union.
  - **Values:** write `Role.ADMIN` / `Role.AGENT`, never `"ADMIN"` / `'AGENT'` — in comparisons (`user.role === Role.ADMIN`), defaults, Prisma data/where clauses and API payloads. Check admin access with `role === Role.ADMIN` (as `requireAdmin.ts`, `AdminRoute.tsx`, `ProtectedLayout.tsx` do), not `role !== Role.AGENT`, so a future role isn't treated as an admin by accident.
  - **Types:** annotate with the enum's type, `role: Role` (e.g. `User` in `UsersTable.tsx`), not `string`.
  - **Lists and validation:** when every role is needed (a zod schema, a select's options, Better Auth's `additionalFields` type), derive it from the enum — `roleSchema` itself, `roleSchema.options`, `Object.values(Role)` — rather than listing values by hand. For per-role labels or styles in new code, use a `Record<Role, …>` map so adding a role becomes a type error until every map handles it.
  - **Setting roles:** pass the role explicitly when creating users (`role: Role.AGENT` in `POST /api/users` in `routes/users.ts`, `Role.ADMIN` in `seed.ts`). Role is server-owned: never accept it from a request body (it isn't a field of `createUserSchema`/`updateUserSchema`, and Better Auth's field is `input: false`).
  - **Adding or renaming a role:** change the Prisma enum, run `bun run db:migrate` then `bun run db:generate` (regenerates `enums.ts`), then update `roleSchema` in `core/src/schemas/users.ts`, the hand-written role lists in `auth.ts` (`user.additionalFields.role.type`) and `client/src/lib/auth-client.ts` (`inferAdditionalFields`), and every display label (e.g. the badge in `UsersTable.tsx`). Run `bun run typecheck` to find the rest.
  - **Tests** (component and e2e) may use string literals (`role: 'AGENT'`), since they assert on the API's JSON. `e2e/fixtures.ts` keeps its own `Role` union for that reason.
- **Admin-only pages (client)** — nest routes under `AdminRoute` (`client/src/components/AdminRoute.tsx`) inside `ProtectedLayout`; non-admins are redirected to `/`. This only hides UI — admin API routes still need a server-side role check: chain `requireAuth, requireAdmin` (`server/src/middleware/requireAdmin.ts`, returns 403 JSON for non-admins) — per route, or once with `router.use(requireAuth, requireAdmin)` for an admin-only router. `server/src/routes/users.ts` is the example.
- **Client** — `client/src/lib/auth-client.ts` exports `authClient` (`better-auth/react`) with no `baseURL`: requests are same-origin and Vite proxies `/api` to the server, so the session cookie works without CORS. Use `authClient.useSession()`, `authClient.signIn.email()`, and `authClient.signOut()`.
- **Route protection (client)** — wrap protected routes in `ProtectedLayout` (`client/src/components/ProtectedLayout.tsx`, see `App.tsx`). It shows a loading state while the session is pending, redirects to `/login` with no session, and renders the `NavBar` (user name + sign out, plus a "Users" link when `isAdmin`). `LoginPage` redirects to `/` if already signed in.
- **Soft-deleted users** — users are never hard-deleted. `DELETE /api/users/:id` (`routes/users.ts`, agents only — admins get 403) sets `User.deletedAt`, rewrites the email to `deleted+<id>+<original>` so the address can be reused, deletes the user's sessions and unassigns their tickets (`assignedToId: null`), all in one transaction. `DeleteUserDialog` invalidates `['tickets']` as well as `['users']` for that reason. Any query for active users must filter `deletedAt: null` (the list, and the existence checks in `PATCH`/`DELETE`, which return 404 for deleted users). `databaseHooks.session.create.before` in `auth.ts` refuses a session for a deleted user. `deletedAt` is not a Better Auth `additionalFields` entry, so read and write it through Prisma, not `internalAdapter`.
- **Rate limiting** — on only when `NODE_ENV=production` (`rateLimit.enabled` in `auth.ts`), with a tighter `/sign-in/email` rule (5 per 60s). Dev and e2e run without it. Production deploys **must** set `NODE_ENV=production`, or sign-in brute-force protection is silently off.
- **Env vars** (`server/.env`) — `BETTER_AUTH_SECRET` (generate with `openssl rand -base64 32`), `BETTER_AUTH_URL` (server URL), `CLIENT_ORIGIN` (Vite dev origin; the server throws on startup without it), `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, optional `SEED_ADMIN_NAME`.

## Inbound email → tickets

The email provider is [AgentMail](https://agentmail.to) (`agentmail` SDK + `svix` for webhook signatures). Mail reaches `ingestEmail` (`server/src/lib/ingest-email.ts`, the behaviour below) two ways: AgentMail's webhook, and a provider-agnostic endpoint that anything else (a forwarding script, a test, e2e) can POST normalised JSON to.

- **AgentMail webhook** — `POST /api/webhooks/agentmail` (`routes/agentmail-webhook.ts`), public, mounted in `app.ts` before `express.json()` with `express.raw` (any content type, 2mb), since the Svix signature covers the raw bytes. Setup and a real round-trip test: `agentmail-setup.md`.
  - **Verification:** svix `Webhook.verify` with `AGENTMAIL_WEBHOOK_SECRET` (unset → 503, bad/missing/expired → 401). svix 2.x `verify()` returns nothing, so the body is `JSON.parse`d after it.
  - **Parsing:** `parseAgentmailEvent` (`lib/agentmail.ts`) uses the SDK's own schemas (`serialization.MessageReceivedEvent` etc., `unrecognizedObjectKeys: "passthrough"`), and copies `from_` to `from` first, since some AgentMail pages show it that way. A payload the schema rejects → 500 (kept for redelivery). Event types other than `message.received/.sent/.delivered/.bounced/.rejected` (spam, blocked, opens, calendar…) → 204.
  - **Delivery rules (AgentMail docs):** at least once, unordered, a 2xx within 15s or it retries (immediately, 5s, 5m, 30m, 2h, 5h, 10h, 10h); an endpoint failing for 5 days is disabled silently. So every event is recorded in `AgentmailEvent` (`agentmail_event`, by `event_id`, not `svix-id`) with `createMany({ skipDuplicates })` **in the same transaction** as its work: a redelivery is skipped (200 `{ duplicate: true }`). Any failure → 5xx so AgentMail redelivers; a P2002 whose event is already recorded → 200.
  - **`message.received`:** only for `AGENTMAIL_INBOX_ID` (compared lowercase), not from the inbox's own address. Body: `extracted_text` (no quoted history), else `text`, else `htmlToText(extracted_html || html)`. With none (a body over 64 KiB comes as `body_url` instead) it's fetched with `inboxes.messages.get`, before the transaction opens. Cut to 100,000 chars. `message_id` / `in_reply_to` / `references` are passed as Message-IDs only when they look like `<x@y>` (unconfirmed that AgentMail's id is the RFC header). Then `inboundEmailSchema` (invalid → 204, logged with a masked address) and `ingestEmail` with `{ threadId, messageId }`. A new ticket → 201 and classification is queued after the commit.
  - **`ingestEmail`** (`lib/ingest-email.ts`, shared with `/api/inbound-email`, runs in the caller's transaction): duplicate by `messageId` or `agentmailMessageId`; else joins the ticket whose `agentmailThreadId` matches, else In-Reply-To/References; else creates the ticket. **AgentMail tickets always start `OPEN`, unassigned, and are never auto-resolved**, so the AI never emails a customer by itself. Two emails of a new thread racing on the unique `agentmailThreadId` → the loser 500s and joins the ticket on redelivery.
  - **Delivery events** find the reply by `TicketMessage.agentmailMessageId` and only move its `emailStatus` forward (`PENDING/FAILED` < `SENT` < `DELIVERED` < `BOUNCED`/`REJECTED`; null = never emailed, left alone). Bounce/reject reasons go to `emailError`. An event for an unknown message under 2 minutes old → 503 (the reply's id may not be stored yet), older → 204. `DELIVERED` means the recipient's server accepted it, not inbox placement.
  - **Logging:** ids, event types and `maskEmail` addresses (`c***@example.com`) only; never bodies, subjects, signatures or full addresses.
- **Endpoint** — `POST /api/inbound-email` (`server/src/routes/inbound-email.ts`). It is not session-authenticated. `requireInboundSecret` (`middleware/requireInboundSecret.ts`) requires `Authorization: Bearer $INBOUND_EMAIL_SECRET` (constant-time compare → 401), and answers 503 when the variable is unset. It is mounted in `app.ts` **before** the global `express.json()`, with its own 1mb parser that runs after the secret check.
- **Payload** — `inboundEmailSchema` in `core/src/schemas/inbound-email.ts`: `from { email, name }` (both required), `subject` (a blank one becomes `"(no subject)"`), `text`, plus optional `messageId`, `inReplyTo`, `references[]` and `receivedAt` (ISO datetime). Invalid → 400 `{ error, fieldErrors }`.
- **Behaviour**:
  - A `messageId` that is already stored → 200 `{ ticketId, duplicate: true }`. Webhooks retry, and a `P2002` race is handled the same way.
  - A reply whose `inReplyTo`/`references` match a stored `TicketMessage.messageId` is appended to that ticket and sets it back to `OPEN` → 200 `{ ticketId, created: false }`.
  - Anything else creates a `Ticket` with its first `TicketMessage` → 201 `{ ticketId, created: true }`.
- **Models** — `Ticket` (auto-increment `Int` id, required `fromName`, `TicketStatus` NEW/PROCESSING/OPEN/RESOLVED/CLOSED (NEW and PROCESSING are for AI auto-resolution, below), optional `TicketCategory?` with no default — set later by AI classification, `assignedTo` → `User`) and `TicketMessage` (body plus email headers) in `schema.prisma`. On the server, use the generated enums (`TicketStatus.OPEN`), as with `Role`. `core/src/schemas/tickets.ts` mirrors them the same way `Role` is mirrored: `ticketStatusSchema`/`ticketCategorySchema` (`z.enum([...])`), plus `TicketStatus`/`TicketCategory` as both values and types. The client imports those from `"core"`. Keep them in step with `schema.prisma` when an enum changes. The inferred types are the same string unions Prisma uses, so a value that one side doesn't have fails the typecheck where it's passed across. It also has `listTicketsQuerySchema` (status/category filters, `sortBy`, `order`) and `updateTicketSchema` (`status`, `category`, `assignedToId`; null clears; at least one field required) for the Phase 4 ticket endpoints.
- **Ticket list** — `GET /api/tickets` (`server/src/routes/tickets.ts`, `requireAuth` — agents and admins) validates the query with `listTicketsQuerySchema` and returns `{ tickets }` with list columns only (no message bodies) plus `conversation`, the `SenderType`s of the latest 8 messages oldest first (`TicketListRow` on the client, drawn by `ConversationStrip` under the subject), sorted newest first by default with `id` as tie-breaker. `sortBy` takes a `ticketSortFieldSchema` value (`id`, `subject`, `fromName`, `status`, `category`, `assignedTo`, `createdAt`, `updatedAt`); `assignedTo` orders by the assignee's name, enums sort in `schema.prisma` declaration order, and nulls follow Postgres (last asc, first desc). The client page is `/tickets` (`TicketsPage` → `TicketsTable`, linked from the `NavBar` for every signed-in user).
- **Ticket table sorting** — `TicketsTable` uses TanStack Table **v9** (`@tanstack/react-table`: `useTable`, `tableFeatures({ rowSortingFeature })`, `table.FlexRender` — not the v8 `useReactTable` API) with `manualSorting: true`: the table only holds the sorting state; the server sorts. Column ids are the `TicketSortField` values, so `sorting[0]` becomes `?sortBy=&order=`, under query key `['tickets', { sortBy, order }]` with `placeholderData: keepPreviousData` (rows stay while a re-sort loads). One column is always sorted (`enableSortingRemoval: false`, default Created desc); each column sets `sortDescFirst` explicitly, since manual sorting can't infer it from data. Headers are buttons with `aria-sort` on the `th`.
- **Ticket table filtering** — the same way: `columnFilteringFeature` with `manualFiltering: true`, filter state in `columnFilters` (column ids `status`, `category`), sent as `?status=&category=` and added to the query key; unset filters are left out of the params. The Status and Category filters above the table are shadcn `NativeSelect`s (a native `<select>`, so tests use `fireEvent.change`), each with an "All …" option that removes the filter, plus a "Clear filters" button while any filter is set. `?category=none` (`UNCLASSIFIED` in `core`, part of `ticketCategoryFilterSchema`) lists tickets with no category. With a filter or search set, an empty result shows "No tickets match your search or filters."
- **Ticket search** — `?search=` (trimmed, max 200; blank = no search) matches subject, `fromName` or `fromEmail` case-insensitively (Prisma `contains` + `mode: "insensitive"`), and `42` / `#42` also matches ticket id 42 (`searchWhere` in `routes/tickets.ts`). It combines with the filters and sorting. On the client it is TanStack's `globalFilter` (`globalFilteringFeature`, manual): the search box updates it immediately, and `useDebouncedValue` (`src/lib/use-debounced-value.ts`, `SEARCH_DEBOUNCE_MS` = 300) delays what goes into the params/query key until typing pauses. "Clear filters" also clears the search.
- **Ticket pagination** — `?page=` (1-based, default 1) and `?pageSize=` (one of `TICKET_PAGE_SIZES` = 10/25/50/100, default `DEFAULT_TICKET_PAGE_SIZE` = 10; both coerced from strings) in `listTicketsQuerySchema`. The response is `{ tickets, total, page, pageSize }`, where `total` counts all matching tickets; a page past the end returns `tickets: []` with the real `total`. The `id` tie-breaker in `orderBy` keeps pages stable. Client: `rowPaginationFeature` with `manualPagination` and `rowCount: total`; `pagination` state (0-based `pageIndex`) is sent as `page`/`pageSize` and is part of the query key. Changing the sort, a filter or the (debounced) search resets to page 1; if the current page is past the end, the table moves to the last page. The footer (`nav` "Pagination") shows "Showing 26–50 of 101 tickets", a "Rows per page" select (`setPageSize` keeps the first visible row on screen) and First/Previous/Next/Last buttons. While a re-sorted/re-filtered list loads, the previous rows stay, dimmed, with `aria-busy` on the table.
- **Ticket detail** — `GET /api/tickets/:id` (`requireAuth`) validates the id with `ticketIdSchema` (`core`; positive int, malformed → 400) and returns `{ ticket }`: the list columns plus `messages` (`id`, `fromEmail`, `fromName`, `body`, `receivedAt`), oldest first; unknown id → 404. The client page is `/tickets/:id` (`TicketDetailPage`), reached from the Subject link in `TicketsTable`. Its route sits under `TicketSplitLayout` (the other signed-in pages sit under `ContentLayout`, the standard `max-w-6xl` width; `ProtectedLayout` adds only the sidebar): from 1440px wide (`useMediaQuery`; narrower, the list isn't rendered or fetched) it shows `TicketQueue` beside the ticket, a sticky list whose current row is a `NavLink` with `aria-current`. Subject links in `TicketsTable` put the list's query in the history state (`TicketListState` = `{ ticketList }`), and the queue shows that same list ("Your ticket list": filters, search, sort, page), validated with `listTicketsQuerySchema` and passed on by its own links; without it (opened directly) it shows the 25 latest ("Latest tickets", `queueParams`). Detail-page tests render `TicketDetailPage` alone, so they never see the queue's request; query key `['tickets', id]`, so invalidating `['tickets']` refreshes it too. A malformed URL id shows "Ticket not found." without a request. Status/category labels and badge variants are shared by both pages in `src/lib/ticket-labels.ts`. Because subjects are `Link`s, `TicketsPage.test.tsx` renders inside a `MemoryRouter`.
- **Ticket updates and assignment** — `PATCH /api/tickets/:id` (`requireAuth`) validates the body with `updateTicketSchema` (`status`, `category`, `assignedToId`; omitted = unchanged, null clears) and returns `{ ticket }` in the detail shape; unknown id → 404. A non-null `assignedToId` must be an active agent (`role: Role.AGENT`, `deletedAt: null`), otherwise 400 with `fieldErrors.assignedToId`. Assignee options come from `GET /api/agents` (`routes/agents.ts`, `requireAuth`: `{ agents: [{ id, name }] }`, active agents by name), because `/api/users` is admin-only. On the client, the detail page's Status, Category and "Assigned to" items are `NativeSelect`s that save on change: `TicketStatusSelect`, `TicketCategorySelect` ("Unclassified" sends `category: null`) and `TicketAssigneeSelect`. Each uses `useUpdateTicket(id)` (`src/lib/use-update-ticket.ts`, one mutation per select), shows the pending choice (`mutation.variables`) while disabled, then `setQueryData(['tickets', id])` and invalidates `['tickets']`; on failure it reverts and shows "Could not update status (…)." etc. via `updateErrorMessage` (the server's `error`, else the HTTP status). Options come from `ticketStatusSchema.options` / `ticketCategorySchema.options` with the labels in `ticket-labels.ts`. A current assignee missing from `/api/agents` stays in the options so the select still shows them (soft-deleting an agent unassigns their tickets, so this is a fallback).
- **Ticket replies** — `POST /api/tickets/:id/replies` (`requireAuth`) validates the body with `createReplySchema` (`core`; `body` trimmed, `REPLY_MIN_LENGTH` (5) to 10,000 chars) and appends a `TicketMessage` written by the signed-in user. It returns 201 `{ ticket }` in the detail shape; unknown id → 404. It sets the ticket's `updatedAt` but not its status. On a ticket that came from AgentMail the reply is emailed to the customer before the response; other tickets are never emailed (see "Outbound email" below).
  - **Who sent a message:** `TicketMessage.senderType` is the Prisma enum `SenderType` (`CUSTOMER | AGENT | AI`, default `CUSTOMER`; `AI` is for auto-resolution, below). Inbound email sets `SenderType.CUSTOMER`; replies set `SenderType.AGENT`. `authorId` → `User` records which agent or admin wrote an `AGENT` message, and is null for customer emails.
  - **Enum mirror:** `core` mirrors the enum as `senderTypeSchema` / `SenderType`, the same way as `Role`. Keep the two in step.
  - **Detail response:** each message includes `senderType` and `author { id, name }`.
  - **Client:** `TicketDetailPage` shows the first message, then "Replies (n)" (later customer emails and agent replies, oldest first, or "No replies yet."), then `TicketReplyForm`.
    - Each message has a Customer/Agent badge (`senderTypeLabels` / `senderTypeVariants` in `ticket-labels.ts`), and agent messages are tinted.
    - `TicketReplyForm` uses the react-hook-form + `Field` pattern with a shadcn `Textarea`. "Send reply" and "Polish" are disabled until the trimmed draft has `REPLY_MIN_LENGTH` (5, from `core`) characters (`useWatch` on `body`), so no "Reply must be at least 5 characters" error is shown; the 10,000-char limit still shows a field error. On success it does `setQueryData(['tickets', id])`, invalidates `['tickets']` and clears the box. On failure it shows "Could not send reply (…)." and keeps the text.
- **Polishing replies (AI)** — `POST /api/tickets/:id/replies/polish` (`requireAuth`) improves a draft with Google Gemini through the Vercel AI SDK (`ai` + `@ai-sdk/google`, `generateText`) and returns `{ body }`; nothing is saved.
  - **Validation and errors:** the body is validated with `polishReplySchema` (`core`, same rules as `createReplySchema`). A missing `GOOGLE_GENERATIVE_AI_API_KEY` returns 503, an unknown ticket 404, and a Gemini failure or empty answer 502 (the error is logged).
  - **Prompt:** the Gemini call lives in `server/src/lib/polish-reply.ts` (`polishReply`, `isPolishConfigured`). It sends the ticket subject, customer name and the last 10 messages (each capped at 4,000 chars) as context. The system prompt tells the model to keep facts and not follow instructions found in the conversation. The model (`GEMINI_MODEL`, default `gemini-3.8-flash`) and the key check are shared by the AI features in `server/src/lib/gemini.ts` (`geminiModel`, `isGeminiConfigured`). Timeout 30s.
  - **Tests:** route tests mock that module (`tickets.test.ts`), so unit tests never call Gemini. Don't add E2E tests that hit the real API.
  - **Client:** `TicketReplyForm` has a "Polish" button (outline, `Sparkles` icon) just before "Send reply". It validates the draft first, then puts the polished text back in the box for the agent to review and send. While it runs, the form is disabled and the button reads "Polishing…". On failure it shows "Could not polish reply (…)." and keeps the draft.
- **Ticket summaries (AI)** — `POST /api/tickets/:id/summary` (`requireAuth`, no body) summarizes the ticket and its conversation with Gemini and returns `{ summary }` (plain text). Nothing is stored: every call generates a fresh summary from the latest messages.
  - **Errors:** malformed id 400, missing `GOOGLE_GENERATIVE_AI_API_KEY` 503, unknown ticket 404, Gemini failure or empty answer 502 (logged).
  - **Prompt:** `server/src/lib/summarize-ticket.ts` (`summarizeTicket`, `isSummaryConfigured`) sends the subject, customer name and the last 30 messages (sender, time, body capped at 4,000 chars; older ones noted as omitted). It passes the system prompt as `instructions` (`system` is deprecated in `ai` v7). Unit tests mock `generateText` (`summarize-ticket.test.ts`) and the route tests mock the module.
  - **Client:** `TicketSummary` sits below the first message on `TicketDetailPage` (keyed by ticket id): an outline "Summarize" button with a `Sparkles` icon ("Summarizing…" and disabled while it runs). Every click regenerates; the previous summary stays, dimmed with `aria-busy`, until the new one arrives, in a tinted `region` named "Summary". On failure it shows "Could not summarize ticket (…)." via `updateErrorMessage`.
- **Ticket classification (AI)** — every ticket created by `POST /api/inbound-email` is classified automatically by a background job, without blocking the webhook. The route only queues a job, `enqueueTicketClassification(ticketId)` (a quick insert), then answers 201.
  - **Job queue:** [pg-boss](https://github.com/timgit/pg-boss) in `server/src/lib/jobs.ts`, on the app's own database. It keeps its tables in the `pgboss` schema, which it creates and migrates itself; Prisma only manages `public`.
    - `index.ts` calls `startJobs()` after `listen`, and a failure there is only logged. It starts pg-boss, creates the `classify-ticket` queue and registers its worker in the API process; `stopJobs()` runs on SIGINT/SIGTERM.
    - With no Gemini key, nothing is started or queued. That is the case in e2e, which also keeps pg-boss away from a test database that doesn't exist yet on a first run. (Email is sent synchronously, not through pg-boss.)
    - Enqueuing never throws: a failure is logged and the email is still accepted.
  - **Retries:** the queue retries a failed job 30 times with exponential backoff (60s base, capped at an hour), roughly a day, so a 429 from an exhausted daily quota or a 503 from overload is retried after it clears. `classifyTicket` sets `maxRetries: 0` so the AI SDK doesn't spend quota retrying too. `createQueue` ignores a queue that already exists, so `startJobs` also calls `updateQueue` to apply changed retry settings. `retryDelayMax` can only be set at creation. Each job keeps the retry settings it was queued with.
  - **Worker:** `classifyStoredTicket(ticketId)` (`server/src/lib/classify-ticket.ts`) loads the subject and first message. It skips a missing or already-categorized ticket, and throws on failure so the job is retried.
  - **How:** `classifyTicket` calls `generateText` with `Output.choice({ options: Object.values(TicketCategory) })`, so Gemini can only answer with a valid category. There is no "unclear" option: the prompt tells it to always pick one, deciding from the subject when the body is empty or unreadable, and to fall back to `GENERAL_QUESTION` when neither is clear. It sends the subject and the first message (capped at 4,000 chars), at temperature 0 with a 30s timeout. Replies that join an existing ticket are not reclassified.
  - **Safety:** after the retries run out the job fails and the ticket stays unclassified for an agent to set. The worker writes with `updateMany({ where: { id, category: null } })`, so a category an agent set in the meantime is never overwritten.
  - **Client:** there is no push. The category shows up the next time the list or detail page is fetched.
  - **Tests:** `classify-ticket.test.ts` mocks `ai` and `db.ts`. The Playwright API server runs with `GOOGLE_GENERATIVE_AI_API_KEY: ''`, which overrides the key Bun would otherwise load from `server/.env`. So in e2e, pg-boss never starts and tickets stay unclassified.
- **Auto-resolution (AI)** — a new ticket from `POST /api/inbound-email` is first offered to the AI, which answers it from the knowledge base (`server/knowledge-base.md`, or `KNOWLEDGE_BASE_PATH`) when it can.
  - **Statuses:** `TicketStatus` has `NEW` and `PROCESSING` before `OPEN` (that order also drives sorting by status). When `isAutoResolveConfigured()` (Gemini key + knowledge base file), a ticket is created `NEW` and an `auto-resolve-ticket` job is queued next to the classification job. Without it, tickets start `OPEN`, as in e2e. The worker moves the ticket to `PROCESSING`, then to `RESOLVED`, or releases it as `OPEN`.
  - **Hidden while processing:** `GET /api/tickets` always adds `status: { not: PROCESSING }`, so agents don't see those tickets (in the page or `total`). `NEW` tickets are listed. The list's Status filter leaves out Processing. The detail route doesn't filter.
  - **Agents can't set AI statuses:** `updateTicketSchema.status` is `agentTicketStatusSchema` (`OPEN`/`RESOLVED`/`CLOSED`, in `core`). `TicketStatusSelect` offers only those, plus a disabled option for a current `NEW`/`PROCESSING` status. A customer reply to a `NEW`/`PROCESSING` ticket sets it `OPEN` as usual, which takes it away from the AI.
  - **Worker:** `autoResolveStoredTicket` (`server/src/lib/auto-resolve-ticket.ts`) reads the knowledge base on every job (edits apply without a restart) and sends it as `instructions`, with the subject, customer name and the customer's emails as data. It uses `Output.object` with `{ canResolve, confidence, reply }`. The prompt says to decline when the knowledge base doesn't fully answer the request, when an escalation rule applies, or when a person has to act. `shouldAutoResolve` also needs `confidence >= MIN_CONFIDENCE` (0.8) and a non-blank reply.
  - **Outcome:** when resolved, one transaction moves `PROCESSING` → `RESOLVED` and stores the reply as a `TicketMessage` with `SenderType.AI` (`AI_SENDER`: "AI Assistant", `SUPPORT_EMAIL`, no `authorId`). The prompt asks for a professional, warm, customer-friendly tone and a plain-text layout: first-name greeting, short paragraphs with blank lines between them, numbered steps / "- " lists, no Markdown, and no sign-off. `formatReply` then tidies the spacing, drops any closing the model added anyway and appends the same `signature()` as polished agent replies (`polish-reply.ts`), signed `AI_SIGN_OFF` ("Support Team"). Otherwise `releaseTicket` moves `NEW`/`PROCESSING` → `OPEN` for an agent. Every write is guarded by the expected current status (`updateMany`), so a ticket an agent or a customer reply has moved on is never overwritten. The AI's answer is **not emailed**; only tickets from `/api/inbound-email` are auto-resolved (AgentMail tickets skip it, see `ingestEmail`).
  - **Failures:**
    - **Gemini:** when `generateText` throws (rate limit, outage, invalid output), the error is logged and the ticket is released as `OPEN` at once. There's no retry, so a customer never waits on the AI and no quota is spent retrying.
    - **Database:** only a database error throws. It leaves the ticket `PROCESSING`, and the queue retries 3 times (30s base, backoff), carrying on from there. After that, pg-boss copies the job to the `auto-resolve-ticket-failed` dead letter queue, whose worker releases the ticket.
    - **Queuing:** if queuing fails, `enqueueTicketAutoResolution` releases the ticket at once.
  - **AI Agent user:** `server/src/lib/ai-agent.ts` (`AI_AGENT_EMAIL` = `ai-agent@helpdesk.local`, `getAiAgentId()`, null when not seeded). A ticket created `NEW` is assigned to it; `releaseTicket` unassigns it (only if still assigned to the AI), and a customer reply that reopens a ticket unassigns it too. A resolved ticket stays assigned to it, which is how the dashboard counts "resolved by AI". It is a `Role.AGENT` user with no credential account (can't sign in), and `humanUserWhere` keeps it out of `/api/agents`, the PATCH assignee check and `/api/users` (list, and 404 on PATCH/DELETE).
  - **`SenderType.AI`:** the client shows it with an "AI" badge (`ticket-labels.ts`), tinted like agent messages. The Gemini prompts name senders via `senderLabels` in `gemini.ts`.
  - **Tests:** `auto-resolve-ticket.test.ts` mocks `ai` and `db.ts` and uses a temp knowledge base via `KNOWLEDGE_BASE_PATH`. In e2e there is no Gemini key, so tickets start `OPEN` and are never hidden.
- **Outbound email (AgentMail)** — agent replies to **tickets that came from AgentMail** (`ticket.agentmailThreadId` set) are emailed to the customer in the same thread, synchronously, inside `POST /api/tickets/:id/replies`. Every other ticket (dummy/seed data, `/api/inbound-email`) is never emailed: its replies keep `emailStatus: null`. AI answers are never emailed (AgentMail tickets skip auto-resolution).
  - **Config:** `isEmailConfigured()` = `AGENTMAIL_API_KEY` + `AGENTMAIL_INBOX_ID`. A reply to an email ticket while it's unset is marked `FAILED` ("Email sending is not configured"), so it can be retried later. e2e: Playwright sets `AGENTMAIL_API_KEY: ''`, and its tickets have no thread anyway.
  - **Status:** `TicketMessage.emailStatus` (`EmailStatus` `PENDING | SENT | FAILED | DELIVERED | BOUNCED | REJECTED`, mirrored in `core`), `emailError` (a short reason, no addresses or content), `agentmailMessageId` (unique).
  - **Send:** the route stores the reply `PENDING`, then `sendReplyEmail(id)` (`lib/agentmail.ts`) `inboxes.messages.reply()`s the ticket's latest customer message that has an `agentmailMessageId`, with `{ text }` and `idempotencyKey: "ticket-message-<id>"` (AgentMail keeps keys 24h, so a retry of a send that did go out isn't sent twice). On success → `SENT` + AgentMail's `messageId`; on any error → `FAILED` + `sendErrorReason(err)` (timeout, 429 limit, 401/403 key, 404, other HTTP, network). It never throws for a send failure, and every write is guarded by `emailStatus: PENDING`. The client is `maxRetries: 0`, `timeoutInSeconds: 10`. The route answers 201 with the reloaded ticket either way, since the reply is saved.
  - **Retry:** `POST /api/tickets/:id/messages/:messageId/resend` (`requireAuth`, `ticketMessageIdSchema` in `core`): 404 if the message isn't on the ticket, 409 unless it is `FAILED` (an `updateMany` guard, so a double click can't send twice), else `PENDING` → `sendReplyEmail` with the same key → `{ ticket }`.
  - **Client:** `EmailStatusNote` (`src/components/EmailStatusNote.tsx`) by each message's time when `emailStatus` is set: `role="status"` with `emailStatusLabels` ("Sending email…", "Emailed", "Delivered", "Email not sent", "Email bounced", "Email rejected"), failures in destructive with `: <emailError>`, and a "Retry sending" button for `FAILED` only (`setQueryData(['tickets', id])` + invalidate `['tickets']`; "Could not retry (…)." on error).
  - **Free plan (AgentMail pricing page, Oct 2026):** 3 inboxes, 100 emails/day, 3,000/month, a "Sent via AgentMail" footer on every email, webhooks included, no custom domains. Over the limit → 429 → "AgentMail's sending limit was reached (HTTP 429)".
  - **Tests:** `lib/agentmail.test.ts` (parsing, `htmlToText`, body fallback/fetch, send success/failure/idempotency) and `routes/agentmail-webhook.test.ts` (svix-signed requests, duplicates, threads, HTML-only/oversized bodies, delivery events) spy on the real client's `agentmailClient().inboxes.messages` methods (`spyOn`) and mock `db.ts`; `lib/ingest-email.test.ts` uses a fake transaction; `tickets.test.ts` spies on `sendReplyEmail`. Never call the real AgentMail API from tests.
- **Resolution time** — `Ticket.resolvedAt` is stamped when a ticket goes from NEW/PROCESSING/OPEN to RESOLVED or CLOSED (agent `PATCH` via `resolvedAtChange` in `routes/tickets.ts`, or AI auto-resolution), kept between RESOLVED and CLOSED, and cleared when it reopens (PATCH to OPEN, or a customer reply). The migration backfilled it from `updatedAt` for tickets already resolved.
- **Dashboard** — `GET /api/dashboard/stats` (`routes/dashboard.ts`, `requireAuth`) returns `DashboardStats` (type in `core/src/schemas/dashboard.ts`): `totalTickets` (all statuses), `openTickets` (OPEN), `aiResolvedTickets` (RESOLVED/CLOSED assigned to the AI Agent), `aiResolvedPercent` (of all tickets, 1 decimal) and `avgResolutionSeconds` (mean `resolvedAt − createdAt` in whole seconds, null when none). All five are computed by the PostgreSQL function `dashboard_stats(ai_agent_email)`, created in migration `20261016040000_dashboard_stats_function`, in one pass over `ticket` with the rounding included. The route only calls `SELECT * FROM dashboard_stats(${AI_AGENT_EMAIL})` and renames the snake_case columns. Prisma doesn't model functions, so change it with a **new** migration (`CREATE OR REPLACE FUNCTION`, or `DROP` + `CREATE` when the returned columns change), never by editing the old one. Route unit tests mock `$queryRaw`, so check SQL changes against a real database. The client page is `/` (`DashboardPage`, "Dashboard" in the `NavBar`): five `Card` tiles (`role="group"` named by their label), durations via `formatDuration` (`src/lib/format-duration.ts`).
  - **Tickets per day:** `GET /api/dashboard/tickets-per-day?timeZone=` (validated by `ticketsPerDayQuerySchema` in `core`: an IANA zone, default `UTC`) returns `TicketsPerDay` = `{ days: [{ date: "YYYY-MM-DD", count }] }` for the last `TICKETS_PER_DAY_DAYS` (30) days, today included, oldest first. The `$queryRaw` uses `generate_series` so empty days come back as 0, and converts `createdAt` (UTC) to the caller's zone before taking the date. Below the tiles, `TicketsPerDayChart` sends the browser's zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`, part of the query key) and draws a bar chart with shadcn `chart` (Recharts 3: `ChartContainer` + `BarChart`, bars in `--chart-2`, hover tooltip). The chart is `aria-hidden`; an `sr-only` table holds the same numbers, and the component tests assert on that table, since jsdom can't lay out Recharts. `DashboardPage.test.tsx` stubs the chart.
- **Env** — `INBOUND_EMAIL_SECRET` in `server/.env` and `server/.env.test` (generate with `openssl rand -base64 32`). `AGENTMAIL_API_KEY`, `AGENTMAIL_INBOX_ID` and `AGENTMAIL_WEBHOOK_SECRET` in `server/.env` for AgentMail. `GOOGLE_GENERATIVE_AI_API_KEY` (and optional `GEMINI_MODEL`) in `server/.env` for reply polishing, ticket summaries and classification; the provider reads the key itself.

## Deployment (Railway or Render)

See `deployment.md` for the steps and variables. In short: one service built from the root `Dockerfile` (`railway.json`: pre-deploy `bun run db:deploy` = `prisma migrate deploy`, health check `/api/health`) plus Railway Postgres.

- **Render:** `render.yaml` (Blueprint) defines the same Docker service plus Render Postgres. Migrations run in its `dockerCommand` before `exec bun src/index.ts` (pre-deploy needs a paid plan). `BETTER_AUTH_URL`/`CLIENT_ORIGIN` fall back to `RENDER_EXTERNAL_URL` in `auth.ts`, and `CLIENT_IP_HEADER=true-client-ip`, since Render appends to `X-Forwarded-For` instead of replacing it.

- **One origin:** with `NODE_ENV=production`, `app.ts` serves `client/dist` after the API routes. `/assets/*` is cached immutably, a missing asset gets a 404, and every other GET falls back to `index.html` (`no-cache`), so client routes work on reload. `BETTER_AUTH_URL` and `CLIENT_ORIGIN` are both the public URL.
- **Client IP:** Railway's edge sends `X-Real-IP`, not `X-Forwarded-For`, so production sets `CLIENT_IP_HEADER=x-real-ip`. `app.ts` then takes the IP from that header instead of `req.ip`, and Better Auth's rate limit uses it via `x-client-ip`.
- **CSP:** helmet's defaults plus `connect-src https://*.sentry.io`. There are no inline scripts: the pre-paint theme script is `client/public/theme-init.js`. Anything loaded from another origin needs a directive in `app.ts`.
- **Build-time variables:** `VITE_*` values are baked into the bundle and must be declared as `ARG` in the Dockerfile to reach a Railway build.
- **Other:** `.dockerignore` keeps `node_modules`, `.env` files and `server/src/generated` out of the image, which regenerates Prisma during `bun install`. The image runs `bun src/index.ts` as PID 1 (user `bun`), so SIGTERM reaches the graceful shutdown.

## Error reporting (Sentry)

Errors only (`tracesSampleRate: 0`, no replay). Each side is off while its DSN is unset, and Playwright sets both DSNs to `''` so e2e never reports.

- **Server** — `@sentry/bun`, initialised in `server/src/instrument.ts`, which must stay the **first import** of `src/index.ts`; `Sentry.close()` flushes on SIGINT/SIGTERM. `captureConsoleIntegration({ levels: ["error"] })` reports every `console.error` (an `Error` argument becomes an exception with its stack), so the 500 handler, job-queue and Gemini failures are reported where they are already logged. To report a new failure, `console.error` it; don't add `Sentry.captureException` next to an existing log. Scripts (`seed.ts`, etc.) don't load Sentry. Env: `SENTRY_DSN`, optional `SENTRY_ENVIRONMENT` (default `NODE_ENV`).
- **Client** — `@sentry/react`, initialised in `client/src/instrument.ts` (first import of `main.tsx`); render errors reach it through React 19's `createRoot` error hooks (`Sentry.reactErrorHandler`). Env in `client/.env` (see `client/.env.example`): `VITE_SENTRY_DSN`, optional `VITE_SENTRY_ENVIRONMENT` (default Vite's mode). The DSN is public, built into the bundle.

## Component tests

Vitest + React Testing Library in jsdom, for the client only. Config is the `test` block in `client/vite.config.ts`; `client/src/test/setup.ts` loads the jest-dom matchers and runs `cleanup` after each test. Reference spec: `client/src/pages/UsersPage.test.tsx`.

**Running**
- `bun run test` (root) or `bun run test` (from `client/`) — run all once. Run this after changing a component that has tests, and before finishing client work.
- From `client/`: `bun run test:watch` reruns on save; `bun run test:ui` opens the Vitest UI (open the tokenized URL it prints). Both need an interactive terminal; in a non-interactive shell Vitest runs once and exits.
- One file or test: `bunx vitest run src/pages/UsersPage.test.tsx` or add `-t "<test name>"`.
- `bun run typecheck` also typechecks the test files (`tsc -b` includes `src/`).

**What goes where — default to component tests**
- Component tests are the main test layer. Every new or changed client component gets them: rendering and states (loading, empty, error, data), conditional UI, form validation, what is sent to the API and how its responses and errors are shown. The API is mocked. They're fast, so cover cases thoroughly here.
- E2E (Playwright, `e2e/`) **only for what no unit test can cover**, because it needs the real browser, server, database and auth working together: sign-in/sign-out, session cookies and revocation, server-side role checks and access control (401/403), database behaviour (constraints, soft delete, duplicates/races, Postgres sorting and pagination), and one critical journey per feature (e.g. an email becoming a ticket an agent can see). For validation or sorting, a few representative cases are enough to prove the server applies them; put the full matrix of cases in unit tests.
- **Never write an E2E test for behaviour a unit test covers or could cover.** That includes UI states, form validation messages, error display, dialog open/cancel, which request is sent, and route logic that works with mocked Prisma. Write a component or server unit test instead. If an E2E test turns out to duplicate unit coverage, delete it. If it covers something unit-testable that has no unit test yet, move it into a unit test.

**Writing a test**
- Put the spec next to the component as `<Component>.test.tsx`. Only `src/**/*.test.{ts,tsx}` is picked up.
- Vitest globals are off: import `describe`, `it`, `expect`, `vi`, `afterEach` from `vitest`.
- Render with `renderWithQuery(<Component />)` from `@/test/render.tsx`. It wraps the component in a fresh `QueryClient` (no shared cache, `retry: false` so error states show immediately) and the app's `TooltipProvider`, and also returns that `queryClient`. `setup.ts` stubs `ResizeObserver` (missing in jsdom) so Radix tooltips can open; focus the trigger to show one (see `DeleteUserDialog.test.tsx`).
- Mock HTTP at the axios boundary: `vi.mock('axios')`, `const mockGet = vi.mocked(axios.get)`, then per test:
  - data: `mockGet.mockResolvedValue({ data: … })`
  - loading: `mockGet.mockReturnValue(new Promise(() => {}))` (never settles)
  - errors: `mockGet.mockRejectedValue(…)` with an `Error` that has `response: { status }` for an HTTP error, or no `response` for a network error. `errorMessage()` only reads those fields.
  - Add `afterEach(() => { vi.resetAllMocks() })`.
- Query like a user: `getByRole` with an accessible name first (`heading`, `table`, `row`, `cell`, `button`, `status` for skeletons), then `getByText`. Avoid test IDs and class names. Use `findBy…` to wait for data, and `queryBy…` with `.not.toBeInTheDocument()` to assert absence.
- Assert user-visible output, including exact copy for messages ("Could not load users (HTTP 403)."). Build locale-dependent expectations (dates) the same way the component does, e.g. `toLocaleDateString()`.
- Components that use routing or the session: wrap in `<MemoryRouter>` from `react-router`, and mock `@/lib/auth-client.ts` with `vi.mock` so `authClient.useSession()` returns the user you need. If a provider is needed in many specs, add a helper next to `renderWithQuery` in `src/test/` instead of repeating it.
- Dismissing Radix dialogs: press Escape with `fireEvent.keyDown(dialog, { key: 'Escape' })`. For an outside click, first wait a tick after opening (Radix attaches its outside listener in a `setTimeout`), then fire **both** `pointerDown` and `click` on `document.body` — Radix waits for the click before closing on a left-button press, so `pointerDown` alone does nothing. See the "Create user dialog" tests in `UsersPage.test.tsx`.
- jsdom has no layout or CSS. Don't test styling, visibility from CSS, or real navigation here; that belongs in E2E.

## Server unit tests

`bun test` (Bun's built-in runner, `import { … } from "bun:test"`), run with `bun run test` from `server/` or the root. Specs sit next to the code as `src/**/<name>.test.ts`. Reference spec: `server/src/routes/tickets.test.ts`.

- Use them for route logic that is cheaper to check without a database: validation branches, which Prisma calls are made and with what arguments, and what is skipped on early returns.
- Mock `../db.ts` (`prisma`) and `../middleware/requireAuth.ts` with `mock.module`, then load the router with a dynamic `await import(...)` **after** the mocks, so the real Prisma client (which needs `DATABASE_URL`) and Better Auth never load. Mount the router on a bare `express()` with `express.json()`, `listen(0)`, and call it with `fetch`.
- Reset the mocks in `afterEach` (`mockReset()`).
- Behaviour that depends on the real database or sessions (constraints, ordering, auth) still belongs in E2E.
- **Schema tests (`core`)** — the shared zod schemas get their own `bun test` specs next to them (`core/src/schemas/<resource>.test.ts`, e.g. `tickets.test.ts` for the reply length rules), run by `bun run test` from `core/` or the root. Test boundaries and error messages there once, instead of repeating the full matrix in route or component tests. `core/tsconfig.json` excludes `*.test.ts`, so `core` stays free of Bun types.

## End-to-end tests

Playwright (Chromium) with `playwright.config.ts` at the root and specs in `e2e/`. The `e2e-tester` agent (`.claude/agents/e2e-tester.md`) owns this suite, and its instructions document how the test stack works.

- **Delegate E2E work** — write, update, run, and debug Playwright tests through the `e2e-tester` agent (Agent tool, `subagent_type: "e2e-tester"`), not in the main session. This covers new specs and helpers in `e2e/` as well as diagnosing failing tests.
- **When to use it** — sparingly. Don't add E2E tests by default after every feature; write component tests first (see "What goes where" above). Use the agent only when a change touches auth, sessions, or server-side role checks, when it adds a critical cross-stack journey the existing specs don't cover, when the user asks for E2E coverage or a test run, or to fix failing specs. When you do, ask for a small number of focused tests, not exhaustive coverage. Tell it which unit tests already cover the feature, so it doesn't add E2E tests for the same behaviour.
- **What to pass it** — the agent starts with no knowledge of this conversation. Tell it what changed or what to cover: the feature and its routes, the files involved, the expected behaviour for each role, and any edge cases. Ask it to run the affected specs and report results.
- **After it returns** — relay its summary to the user: tests added or changed, pass/fail counts, and any app bugs it found. Don't claim tests pass unless its report shows a passing run.

## Conventions

- Use Bun, not npm/yarn/pnpm.
- All API routes live under `/api`.
- Express 5 forwards rejected promises from async handlers to the error middleware — no try/catch wrappers needed just to call `next(err)`.
- Server imports use explicit `.ts` extensions (`import { app } from "./app.ts"`).
- Style the client with Tailwind utility classes; no separate CSS files per component.
- UI components come from shadcn/ui (Radix base, Nova preset, neutral). Add them from `client/` with `bunx --bun shadcn@latest add <component>`; they land in `src/components/ui/`. Use theme tokens (`bg-background`, `text-muted-foreground`, `text-destructive`, …) instead of raw palette colors. Import from `client/src` with the `@/` alias.
- **Theme** — Instrument Sans (`@fontsource-variable/instrument-sans`); teal primary. Besides shadcn's tokens, `index.css` defines one color per voice — `customer` (slate), `ai` (indigo), `agent` (teal) — each with `-soft`/`-soft-foreground`, plus `attention` (amber, for OPEN tickets). Use them only for what they mean: badge variants `customer`/`ai`/`agent`/`attention`, the Button `ai` variant for actions that ask the AI (Summarize, Polish), message tints/avatars, and `BrandMark`. The layout is a sidebar (`NavBar`, `NavLink`s with `TextLink`'s `sidebar` variant) that becomes a top bar below `md`.
- **Dark mode** — `ThemeToggle` in the sidebar offers light / dark / system (`useTheme` in `src/lib/theme.ts`, saved in `localStorage` under `helpdesk-theme`, default system). It toggles the `dark` class on `<html>`; `client/public/theme-init.js` (loaded by `index.html`; a file because the CSP blocks inline scripts) applies the saved choice before first paint, so keep the key and rule there in step with `theme.ts`. Every color token has a `.dark` value in `index.css`; new colors need both.
- Text links use `TextLink` (`src/components/TextLink.tsx`, a react-router `Link` with cva variants): `variant="default"` for links in content (underline on hover), `variant="nav"` for navigation (muted, `text-foreground` on hover). Don't repeat hover/color classes on a bare `Link`; pass only layout classes. Add a variant for a new style. A link that looks like a button is `<Button asChild><Link /></Button>`.
- `cn` comes from the `cn` npm package (shadcn's drop-in replacement for clsx + tailwind-merge), not a local clsx/twMerge helper.
- **Data fetching: always use axios + TanStack Query (React Query)** for client calls to `/api`. Never use `fetch`, and never use `useEffect` + `useState` to load server data.
  - Reads: `useQuery({ queryKey, queryFn: () => axios.get<T>(url).then((res) => res.data) })`. See `UsersTable.tsx`.
  - Writes (create/edit/delete): `useMutation` with an axios call, then `queryClient.invalidateQueries({ queryKey })` on success so lists refetch.
  - The shared `queryClient` is in `client/src/lib/query-client.ts`. It registers `AxiosError` as the default error type, retries only network/5xx errors, and exports `errorMessage(error)` for display. `NavBar` clears the cache on sign-out.
  - Exception: auth calls go through `authClient` (Better Auth), not axios.
- Build forms with react-hook-form + zod using shadcn's `Field` pattern: `<Controller>` → `<Field data-invalid>` → `FieldLabel` / `Input aria-invalid` / `FieldError`. Show server errors via `form.setError('root.serverError', …)` rendered in a destructive `Alert`. See `LoginPage.tsx`.
  - Every form uses this pattern, including dialogs. Adding a user is the example: `UserForm.tsx` renders only the form (fields, server-error `Alert`, and `children` for the action buttons) and takes the `useForm` instance as a prop; `CreateUserDialog.tsx` owns that instance (the shared zod schema + `zodResolver`), the mutation, `form.reset()` when the dialog closes, and the mutation's `onError` that puts the server's `error` message into `root.serverError`. Keep form fields in their own component like this so other containers can reuse them: `EditUserDialog.tsx` (pencil button per row in `UsersTable`) renders the same `UserForm` with `passwordOptional` and its own `idPrefix`, pre-filled from the row, and sends `PATCH /api/users/:id` (validated by `updateUserSchema`, where a blank password means "keep the current one"; a new password revokes the user's other sessions).
  - Destructive actions are confirmed in an `AlertDialog` (no outside-click dismiss), not a `Dialog`: see `DeleteUserDialog.tsx`. Its confirm button is a plain `Button` calling `mutate`, not `AlertDialogAction` (which closes immediately), so the dialog stays open to show a server error. A disabled action that needs an explanation wraps the disabled button in a focusable `<span>` inside a `Tooltip` (`TooltipProvider` is set up once in `main.tsx` and in `renderWithQuery`).
  - Validate the same input on the server with zod (`schema.safeParse(req.body)` → 400 with `{ error, fieldErrors }` via `sendValidationError` from `server/src/lib/validation.ts`), as `POST /api/users` in `routes/users.ts` does.
- **Zod schemas live in `core`, never inline in client or server.** Any schema for data that crosses the API (request bodies, query params) is defined once in `core/src/schemas/<resource>.ts`, exported along with its inferred type (`export type CreateUserInput = z.infer<typeof createUserSchema>`), and re-exported from `core/src/index.ts`. Both sides import it from `"core"`: the client form passes it to `zodResolver` and uses the type for `useForm<…>`/the mutation; the server router calls `.safeParse(req.body)`. Don't copy or re-declare a schema on either side — one definition means the rules and error messages can't drift. `createUserSchema` (used by `CreateUserDialog.tsx` and `routes/users.ts`) is the example. Server-only concerns (e.g. uniqueness checks against the database) stay in the route handler, not the schema. Transforms like `.trim()`/`.toLowerCase()` are fine — they also run in the client before submit.
- `src/components/ui/` files are ours and may be customized. `input.tsx` has an autofill reset that hides Chrome's autofill background — re-apply it if the component is regenerated with `shadcn add input --overwrite`. `dialog.tsx` and `alert-dialog.tsx` open faster than shadcn's default (`data-open:duration-50` on the overlay and content, so modals appear in 50ms instead of 100ms) — re-apply that after regenerating either.
- Secrets go in `server/.env` (git-ignored); document new variables in `server/.env.example`.
